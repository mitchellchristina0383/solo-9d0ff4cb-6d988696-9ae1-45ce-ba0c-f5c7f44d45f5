# NetworkPolicy 清理演练（Flask 单命名空间）

集群里重叠的 NetworkPolicy 越积越多时，用这个页面在**单命名空间**内演练“等价清理”：
录入 Pod 标签和最多 10 条策略，勾选候选可删项，一键求出**数量最大**的一组可整体删除、
且删除前后每对 Pod 各方向连通结果完全相同的策略。

## 1. 语义规则（按需求简化）

- 标签选择器只支持**等值匹配** `key=value`，多个要求之间是 AND；忽略端口、IP 段、跨命名空间对端。
- 空 Pod 选择器 = 选中本命名空间全部 Pod。
- 对端选择器每行一个；`*` 单独一行 = 空选择器（全选）；对端框留空 = 没有任何允许对端（选中即拒绝）。
- Pod 在某方向（入站/出站）**没有被任何策略选中**时，该方向**默认放行**。
- 一旦被选中，取所有选中策略在该方向允许对端的**并集**。
- 两 Pod 连通须**同时**满足：发端出站允许 + 收端入站允许。
- 连通矩阵覆盖全部有序 Pod 对（含自身对），行是发端、列是收端。

## 2. 求解算法

策略数上限 10，候选子集至多 2^10 = 1024 个，直接穷举：

1. 计算当前标签下的完整连通矩阵 `before`；
2. 只在**勾选了“可删”**的策略下标中，按子集大小从大到小枚举（同大小按策略名字典序排序）；
3. 对每个候选子集，用剩余策略重算矩阵，与 `before` 完全相等即命中，返回第一个命中组；
4. 页面展示实际删除的策略名、删除前后两张连通矩阵，有差异的格子会高亮（正常求解不会出现）。

平局规则保证结果确定可复现：同数量多组等价时取策略名字典序最小的一组。

注意一个符合 K8s 语义的边界：如果某方向的策略被**全部删光**，该方向会回落到“默认放行”，
这本身也可能改变连通矩阵（例如原本靠“选中即拒绝”实现的隔离）。求解器把这种情况视为不等价，
因此承担隔离职责的策略不会被误删。

## 3. 目录结构

```
app/
  __init__.py        # Flask 应用工厂与路由（GET /、POST /clean、GET /healthz）
  solver.py          # 选择器匹配、双向连通判定、矩阵、穷举求解
  parser.py          # 表单解析与校验（标签语法、重名、10 条上限、方向必选等）
  seed.py            # 内置演练场景与表单原始值 <-> 视图行转换
  templates/
    index.html       # 单页：录入区 + 结果区，原生 JS 负责增删行与提交前重编号
wsgi.py              # gunicorn 入口（容器使用）
tests/               # 28 个 unittest 用例（求解器语义 + 解析器 + Flask 端到端）
Dockerfile
docker-compose.yml
requirements.txt
```

## 4. 用 Docker Compose 启动

```bash
docker compose up --build
# 打开 http://localhost:8000
```

容器以非 root 用户运行 gunicorn（2 worker），内置 `/healthz` 健康检查并在 compose 中声明。
停止：`docker compose down`。

不用容器时的本地运行方式：

```bash
python -m venv .venv && . .venv/bin/activate
pip install -r requirements.txt
gunicorn --bind 0.0.0.0:8000 wsgi:application
# 或开发模式：flask --app app run --debug
```

## 5. 页面操作

- Pod 行：名称 + `key=value,key=value` 标签；可随时增删。
- 策略行：名称、Pod 选择器、入站/出站开关、两个方向的对端选择器（多行）、“可删”勾选。
- “添加策略”在达到 10 条时自动禁用；提交前 JS 会把所有行重新连续编号，
  因此中途删除任意行都不会出现下标空洞。
- 点击“清理（按当前标签求解）”后，页面保留完整录入区且**标签仍可继续修改**，
  被删除的策略行会出现红色“本次已删除”徽标，可在修改后再次提交求解。
- “重置为演练数据”回到内置场景。

内置场景（6 Pod / 8 策略）包含：两条完全重复的入站策略、一条更宽的入站策略、
一对仅在现有标签下等价的出站策略，以及不可删的入站/出站隔离策略。

## 6. 实测记录

交付前在本机（Python 3.11，无 Docker 守护进程，故容器部分为静态核对）完成：

- `python -m unittest discover -s tests`：**28/28 通过**，覆盖
  默认放行、并集语义、双向门、空对端拒绝、通配对端、最大等价子集、字典序平局、
  10 条穷举、解析器各类非法输入、Flask 路由 200/400 等。
- 用与容器相同的 gunicorn 命令起真实 HTTP 服务做黑盒验证：
  - 种子场景 POST `/clean` 返回删除 3 条
    （`p-web-ingress-dup-a`、`p-web-ingress-dup-b`、`p-web-egress-a`），
    两张矩阵 0 个差异格，3 个删除徽标；
  - **成批删除**：只勾选两条重复入站策略时，只删这 2 条，未勾选策略不受影响；
  - **求解时改标签**：把 `web2` 的 `tier` 改成 `backend` 后重新提交，
    删除清单中的出站策略由 `p-web-egress-a` 变为 `p-web-egress-b`，新标签在录入区回填；
    另有专门用例验证改标签可让冗余策略变成唯一屏障（可删数 2 → 1）；
  - 非法标签返回 HTTP 400，错误横幅提示且原始输入回填；
  - 无候选可删时明确提示“没有找到可安全删除的策略组”。
- 前端 JS：语法解析通过；用 Node + 最小 DOM 桩验证了提交前重编号、
  10 条硬上限与按钮禁用、删行后下标重新连续、Pod 增行等逻辑。
- Docker 相关文件做了静态核对：基础镜像、依赖固定版本、非 root 用户、
  暴露端口、健康检查指令、compose 端口映射与 healthcheck 齐全。

## 7. 余项与限制

- 运行环境没有 Docker 守护进程，**未实际执行 `docker compose build/up`**；
  已用同版本 gunicorn 在本地验证应用本身，Dockerfile/compose 仅静态核对，
  建议在有 Docker 的机器上跑一次 `docker compose up --build` 收尾确认。
- 仅模拟等值标签选择器与单命名空间场景；真实 NetworkPolicy 的端口/协议、
  namespaceSelector、ipBlock、except、策略优先级等未建模。
- 求解为同步穷举（上限 10 条、Pod 数量无硬限制但矩阵为 N²），
  演练规模下耗时在毫秒级；若放宽策略上限需要改成分支限界或其他搜索。
- 页面无持久化，刷新即回到内置种子数据；演练工具定位，未接数据库。
